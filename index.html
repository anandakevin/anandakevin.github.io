Featured writing · case study

Repeatable API-gateway delivery across environments

How I made API-gateway configuration easier to review and promote across environments.

Tagsplatform · integration · go · krakend
Open full case study ↗

Case-study summary

from the case study

Context

Gateway configuration had been handled differently in each environment. That made reviews manual and made it hard to see what changed during promotion.

→

Constraints

Changes must be reviewable in version control. Non-production and production may differ, but reviewers need to see exactly how.

→

Approach

Separate environment-specific settings — put them in named configuration layers so reviewers could see what changed between environments. Use one promotion pipeline — validate, package, and apply gateway configuration through the same documented steps. Document the gateway responsibilities — record where routing, authentication hooks, and rate limits were owned so operators could find the answer quickly.

Featured writing · case study

Configuration playground for domain experts

An internal playground where analysts could test assessment-rule changes without production access or one-off engineer scripts.

Tagsfintech · internal-tools · backend
Open full case study ↗

Case-study summary

from the case study

Context

Loan assessment logic changes often start with analysts who understand credit policy but cannot safely experiment in production. Testing a policy change often required an engineer to run a script or interpret spreadsheet changes before analysts could compare the result.

→

Constraints

No customer or production data in the playground; synthetic inputs only. Changes must be explainable to compliance-minded reviewers, not only to the author. The tool should complement — not replace — the authoritative servicing systems.

→

Approach

Keep policy exploration separate from execution — give analysts configurable scenarios with named inputs and expected outputs they could compare. Define what could change — show which parameters were editable, which were fixed, and which needed an engineering release. Save useful scenarios — use them as regression cases when a policy changed again next quarter.

Featured writing · case study

Legacy batch jobs to SQL pipelines

Moving COBOL-era batch processing toward observable, idempotent ETL while keeping the remaining mainframe work in view.

Tagsetl · legacy-systems · data-pipelines
Open full case study ↗

Case-study summary

from the case study

Context

A General Ledger organization still depended on a large COBOL batch estate. Teams needed faster change cycles, better observability, and pipelines that could survive retries without corrupting accounting state.

→

Constraints

Financial correctness mattered more than migration speed; partial automation could be worse than slower automation with evidence. Operations were still organized around batch windows, logs, and runbooks, so new tooling had to fit those workflows. Jobs still needed to show which environment and ledger slice they touched.

→

Approach

Inventory the real batch graph — which jobs are pure transform, which encode business rules, which are safe to parallelize. Move selected jobs incrementally to SQL-based ETL — with explicit logging and idempotency at load boundaries, while leaving jobs that still needed the legacy path in place. Instrument for operators — log parsing and replay-friendly steps so retries could be performed intentionally and traced afterward. Add internal tooling — a full-stack, metadata-driven parameter dashboard with soft locks, versioning, audit logs, and approval workflows so report owners no longer had to request production edits by email. Revamp the dashboard safely — clean architecture, atomic models, and decoupled metadata made the parameter workflow easier to scale and reuse.
