System assessment before commitment

Why I like writing a short system assessment before a team commits to a rewrite.

System assessment before commitment

Before a large rewrite, I prefer to write down what is in scope, what can go wrong, and which risks the team is willing to take. Without that, people can agree on the goal while assuming different constraints.

What an assessment should answer

  • Interfaces — which APIs and integration points are in scope, and which legacy seams are explicitly out of scope for this phase.
  • Security and trust boundaries — where authentication, authorization, and data residency assumptions change if the design ships.
  • Latency and operations — what gets worse under load, and which monitoring needs to exist on day one rather than later.

Why it is not a design doc

An assessment can conclude with “do not proceed without X” or “consolidate these two systems first.” That can save months of incremental rework.

Related work context

I used this approach during a fintech platform period, while looking at core-banking evaluation and user-management consolidation before gateway and deployment work accelerated. The gateway case study shows what we built afterward; this note is about the assessment that came first.
